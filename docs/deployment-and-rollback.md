# انتشار و بازیابی فروشگاه

**وضعیت: منتشر نشده است.** این شاخه و تمام ERP و داده‌های آزمایش فقط محلی‌اند. سایت اصلی، پورت 18082، noindex، داده مشتری و سرویس‌های دیگر تغییر نکرده‌اند. پرداخت واقعی یا استقرار بدون تأیید صریح مالک مجاز نیست.

## پیش‌نیازهای انتشار

۱. تهیه قیمت، موجودی افتتاحیه، واحد و تبدیل قرقره، شماره فنی و مجوز رسانه از مالک؛ رفع flag هر محصول. موجودی افتتاحیه باید سند واقعی انبار داشته باشد.
۲. انتخاب adapter واقعی درگاه و بررسی مستندات فعلی آن؛ credential sandbox، تأیید سمت سرور، واحد پول، idempotency، پرداخت دیررس، refund و settlement با شواهد ارائه‌دهنده آزمون شوند. صرف allowlist کردن نام یک gateway تأیید صحت آن نیست.
۳. شرکت/سال مالی/حساب‌ها، مالیات و شناسه‌های قانونی، هزینه ارسال و خدمات پیام با مسئول کسب‌وکار تأیید شوند. نرخ مالیات یا انطباق قانونی حدس زده نشده است.
۴. ERP تولیدی روی میزبان دارای ظرفیت تأییدشده و شبکه خصوصی/TLS معتبر نصب شود. این سرور مشترک ۴GB برای اضافه‌کردن ERP تأیید ظرفیت ندارد. compose محلی را روی آن اجرا نکنید.
۵. worker/cron قابل اعتماد، کنترل خطا، rotation اسرار، پایش صف معوق و backup خارج از میزبان آماده شود؛ WP-Cron وابسته به بازدید به‌تنهایی SLA عملیات نیست.
۶. بازیابی یک backup تازه **همان تولید** در محیط جدا، با مقایسه داده و فایل و آزمون ورود و درخواست عمومی انجام شود. نتیجه synthetic محلی جای آن نیست.

## نسخه پشتیبان

قبل از هر مهاجرت، SQL تراکنشی، کل wp-content شامل MU-pluginها/فایل/فونت، compose و env خصوصی و پیکربندی Nginx همان سایت ذخیره شوند. فایل‌ها با دسترسی محدود و checksum نگه داشته شوند؛ به Git یا گزارش عمومی منتقل نشوند. backup موجود 20261013-123014-visual-release فقط SQL و theme داشت و جای backup کامل نیست.

نسخه‌های محلی rehearsal در `.local/backups` و private/backups سایت Frappe هستند. ابزار `recovery-rehearsal.py` فقط در containerهای نام‌گذاری‌شده محلی کار می‌کند، مقصد DB/site/volume جدید می‌سازد و منبع را overwrite نمی‌کند. برای ERP کلید encryption باید همراه backup خصوصی بازیابی شود. scheduler و ایمیل سایت بازیابی‌شده باید خاموش بمانند.

پیشنهاد برنامه خودکار پس از تأیید انتشار: SQL و فایل افزایشی روزانه، نسخه کامل هفتگی، انتقال رمز‌شده خارج میزبان، هشدار failure و آزمون بازیابی دوره‌ای. timer/cron تولید هنوز نصب نشده است؛ سیاست retention پس از تعیین حجم/نیاز مالک اعمال می‌شود و هیچ backup قدیمی خودکار حذف نشده است.

## انتشار محدود و قابل بازگشت

- HEAD و drift فایل‌های زنده دوباره hash شوند. فایل class-quotes و bootstrap 0.3.1 بازیابی‌شده حفظ شوند. تغییر unrelated lab rewrite نصب نشود.
- diff و آزمون نهایی مرور شود؛ allowlist این تغییر عمدتاً `site/plugins/tehnet-store` و اصلاح capability دو فایل Core است. اسکریپت قدیمی deploy-theme-plugin.sh کل Core را کپی می‌کند؛ برای این انتشار از آن استفاده نکنید.
- ابتدا فایل افزونه جدید، سپس نقش‌ها و اتصال غیرفعال نصب شوند. schema ERP و custom fields با backup و migration سازگار اضافه شوند. هیچ جدول موجود حذف نمی‌شود.
- import در production در خود کد بسته است. ابتدا manifest و اجرای dry-run بررسی شوند؛ مهاجرت تأییدشده باید روی snapshot/staging بازیابی‌شده انجام و نتیجه محصول به محصول تأیید شود. صرف تغییر WP_ENVIRONMENT_TYPE برای دورزدن این guard روش انتشار نیست.
- بعد از تأیید موجودی/قیمت و adapter، فعال‌سازی فروش جداگانه انجام شود. noindex تا مجوز مستقل راه‌اندازی حفظ شود.
- تعداد orders/products، checkout، نقش‌ها، اسناد GL، صف و fingerprints سرویس‌های غیر TehNet قبل/بعد مقایسه شوند.

## برگشت

در خطای نمایش، فروش فیزیکی را با خاموش‌کردن flag رزرو ببندید؛ مشتری جدید نباید به پرداخت هدایت شود. نسخه قبلی افزونه allowlist‌شده از backup برگردد. database را کورکورانه به گذشته برنگردانید: سفارش یا رسید جدید ممکن است وجود داشته باشد. ابتدا سفارش‌های در حال پرداخت، رزروها، تراکنش بانک و outbox تطبیق داده شوند.

سند submitted مالی با حذف SQL اصلاح نمی‌شود؛ native cancellation/return/credit note و Payment Entry مرتبط استفاده شوند. rollback کاتالوگ فقط محصول draft دست‌نخورده همان run را soft-trash می‌کند و ویرایش انسانی را رد می‌کند. دسته‌ها برای جلوگیری از تخریب داده مشترک نگه داشته می‌شوند.

lock معوق `tn_erp_order_lock_ID` یا importer را فقط پس از بررسی نتیجه احتمالی سمت ERP باز کنید. retry همان payload و key است؛ برای فرار از تضاد payload کلید جدید نسازید. تغییر terms سفارش رزروشده نیاز لغو و سفارش جدید دارد.

## ادامه پرداخت آزمایشی — ۱۵ اکتبر ۲۰۲۶

فایل `ops/staging/payment-sandbox.compose.yml` overlay صریح آزمایش محلی است؛ prepare-local آن را اجرا نمی‌کند و روی این محیط اعمال نشده است. هرگز در تولید استفاده نشود. حذف overlay و اجرای base compose با همان volumes flags آزمایشی را کنار می‌گذارد؛ سپس درگاه در Woo خاموش شود. receipt/attempt و outbox برای حسابرسی نگهداری شوند؛ پاک‌کردن آن‌ها روش بازیابی نیست.

Docker named pipe در sandbox فعلی در دسترس نیست؛ بازسازی container/WP-CLI و native gateway checkout هنوز شرط بازند. نه backup/restore تولید و نه استقرار از این مرحله مجاز/اجرا شده‌اند. جزئیات قفل ماندگار و unknown request در docs/payment-sandbox-fa.md.


## به‌روزرسانی انتشار آنلاین — ۱۵ اکتبر ۲۰۲۶

مطالب محدودیت Docker/عدم استقرار در بخش‌های قبلی، گزارش مراحل پیشین‌اند. وضعیت فعلی: کاتالوگ استعلام عمومی https://tehnet.ir/shop/ و پنل https://tehnet.ir/wp-admin/admin.php?page=tn-store منتشر شده‌اند. ERP و پرداخت واقعی تولید غیرفعال‌اند. صفحه اصلی و theme و سرویس‌های دیگر حفظ شدند.

پشتیبان کامل خصوصی `/root/tehnet-backups/20261015-184219-store-review` شامل SQL، کل WordPress، config/env و Nginx است. همان تولید در DB/volume محلی جدید بازیابی، همه فایل‌ها و ۹ جدول تطبیق و HTTP 200 تأیید شد؛ mail و HTTP خروجی clone بسته است. `production-recovery.json` شاهد است.

انتشار allowlist با `deploy-store-review.py`، import صریح WP CLI مجاز با SHA256 و dry-run پیش‌فرض، سپس انتشار استعلام با `publish-inquiry-catalog.php` انجام شد. import عادی production هنوز بسته است و environment تغییر نکرده. rerun تولید صفر create و ۲۵ skip داد. `ensure-store-pages.php` نگاشت صفحات native منتشرشده را با حفظ draftهای قدیمی درست کرد. `deploy-store-media.py` فایل‌های رسانه/مهر را با backup و guard drift منتشر کرد. جزئیات `production-release.json` و `production-media-release.json`.

برای rollback، افزونه Store را غیرفعال و فقط فایل‌های allowlist از checkpoint مربوط برگردانید. SQL را کورکورانه به عقب نبرید؛ داده/صفحه/audit جدید یا ویرایش انسانی باید تطبیق شود. گزینه coming-soon، متن قبلی shop و وضعیت/عنوان کالای جدید در option `tn_public_inquiry_release_20261015` محفوظ‌اند. صفحه اصلی در این مهاجرت‌ها هدف نبوده است.

آزمون مرورگر تولید در `live-browser.json`: منوی اصلی → shop عمومی، ۲۵ کالای غیرقابل خرید، مقایسه مهمان، تصاویر اختصاصی، چرخش شماتیک، موبایل بدون overflow و HTTP 200 صفحات. Store API خود Woo مقدار قیمت unset را به رشته صفر serialize می‌کند؛ `is_purchasable=false` و `price_html=استعلام` و قیمت ذخیره‌شده خالی است؛ این پیشنهاد فروش رایگان نیست.

خرید native رسمی sandbox محلی با سفارش ۲۵۲ / ۳۵۰۰ ریال و فاکتور ERP و callback تکراری گذشت (`native-payment.json`). هیچ وجه واقعی جابه‌جا نشد. تصویرسازی و مدل گروه کالا دقیق نیستند و با برچسب شماتیک عرضه می‌شوند؛ عکس واقعی/GLB معتبر همچنان وابستگی باز است.
