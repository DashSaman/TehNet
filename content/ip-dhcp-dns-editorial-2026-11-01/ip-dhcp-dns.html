وقتی یک دستگاه IP دارد اما سرویس باز نمی‌شود، «تغییر DNS» یا ساختن دوبارهٔ DHCP نقطهٔ شروع خوبی نیست. ابتدا معلوم کنید آدرس و prefix درست دریافت شده، مقصد چگونه مسیریابی می‌شود و نام را کدام resolver پاسخ می‌دهد. این درس از مسیر MTCNA تهران نتورک، رابطهٔ IP، DHCP و DNS را با یک طرح ساختگی و مسیر عیب‌یابی مرحله‌ای توضیح می‌دهد.

دامنه و حد آزمون: مثال‌ها IPv4 و یک LAN ساده، بدون policy routing یا VPN هستند. منابع رسمی در ۱ نوامبر ۲۰۲۶ بازبینی شدند؛ انتخابگر مستندات MikroTik نسخهٔ 7.26 را نشان می‌داد، نه نسخهٔ دستگاه شما یا توصیهٔ ارتقا. فرمان‌های RouterOS و سناریوی DHCP/DNS این متن اجرا نشده‌اند؛ خروجی واقعی، زمان رفع یا موفقیت لاب ادعا نمی‌شود. پیش از تغییر تنظیمات، پشتیبان و روش بازگشت لازم است.

ویدیوی قبلی همین جلسه در YouTube حفظ شده است؛ متن مستقل خوانده می‌شود. اجرای همهٔ دستورهای ویدیو در نسخهٔ فعلی در این بازبینی تأیید نشده است.

۱. IP و prefix: مقصد کنار من است یا به gateway نیاز دارد؟

در مرجع ip/address، address و netmask برای محاسبهٔ network به‌کار می‌روند. داشتن چهار عدد شبیه هم کافی نیست؛ prefix و مسیر واقعی را هم بررسی کنید. در طرح سادهٔ زیر، کلاینت با /24 مقصد .140 را در همان subnet می‌بیند؛ اگر فقط prefix کلاینت اشتباهاً /25 باشد، .100 و .140 در دو subnet متفاوت قرار می‌گیرند. نتیجه لزوماً قطعی کامل نیست؛ مسیر از gateway و قواعد عبور ممکن است نتیجه را عوض کند.

Illustration only — not customer addresses or a ready-to-run lab
LAN:       192.0.2.0/24
Gateway:   192.0.2.1
DNS:       192.0.2.53  (separate, already prepared lab server)
Printer:   192.0.2.60  (planned manual address)
DHCP pool: 192.0.2.100–192.0.2.150
Client A:  192.0.2.100/24
Target B:  192.0.2.140/24

A with /24 -> same subnet as B
A with /25 -> A:192.0.2.0/25, B:192.0.2.128/25

این آدرس‌ها مطابق RFC5737 فقط برای مستندسازی‌اند؛ آن‌ها را به اینترنت نفرستید یا طرح عملیاتی فرض نکنید. برای اجرای لاب، همهٔ آدرس‌ها را یکجا با طرح خصوصیِ مجاز و بدون تعارض جایگزین کنید. هم‌subnet بودن در این مثال جای خواندن جدول مسیر را نمی‌گیرد؛ route اختصاصی‌تر، VPN یا سیاست مسیریابی می‌تواند تصمیم واقعی را تغییر دهد. جزئیات در درس مسیریابی آمده است.

۲. DHCP چهار جزء جدا دارد؛ DNS همان gateway نیست

  • آدرس روی رابط LAN، خودِ روتر را عضو شبکه می‌کند. روی bridge، رابط واقعی و عضویت پورت‌ها را بررسی کنید؛ نام ether2 در هر دستگاه الزاماً LAN نیست.
  • Pool محدودهٔ آدرس‌های قابل تخصیص است؛ آدرس روتر را داخل آن نگذارید.
  • DHCP Server سرویس را به رابط و pool متصل می‌کند؛ DHCP Network گزینه‌هایی مانند prefix، gateway و DNS را برای subnet مشخص می‌کند.
  • Gateway برای مسیر خروج از subnet است. DNS برای تبدیل نام به پاسخ DNS است؛ یک آدرس می‌تواند هر دو نقش را داشته باشد، اما یکی جای دیگری را نمی‌گیرد. داشتن gateway به‌تنهایی اینترنت یا مسیر بعدی روتر را تضمین نمی‌کند.

مرجع DHCP Server پیش‌نیازهای آدرس، pool، network و رابط را جدا می‌کند. مثال مفهومی زیر تغییر پیکربندی است، نه دستور تعمیر شبکهٔ زنده. فقط روی لاب خالی و جدا، پس از جایگزینی طرح آدرس و با bridge ازقبل‌آمادهٔ lab-lan معنا دارد؛ نام‌های هم‌منظور نباید از قبل وجود داشته باشند. اجرای دوبارهٔ add را idempotent فرض نکنید. DNS نمونه یک سرور جدا و ازقبل‌آماده است؛ این قطعه DNS یا دسترسی اینترنت ایجاد نمی‌کند.

# Conceptual only; adapt the entire address plan in an isolated lab.
# Requires an existing lab-lan bridge with a lab client port.
/ip/address/add address=192.0.2.1/24 interface=lab-lan comment="TN-LAB-C01"
/ip/pool/add name=tn-lab-c01 ranges=192.0.2.100-192.0.2.150
/ip/dhcp-server/network/add address=192.0.2.0/24 gateway=192.0.2.1 dns-server=192.0.2.53
/ip/dhcp-server/add name=tn-lab-c01 interface=lab-lan address-pool=tn-lab-c01 disabled=yes

سرویس در نمونه عمداً disabled می‌ماند. تا جدابودن لاب، درستی رابط و نبود DHCP رقیب تأیید نشده، آن را فعال نکنید. این قطعه طرح آموزشی است و روی RouterOS آزموده نشده؛ برای تکمیل اجرا، دستور و رفتار را با نسخهٔ خود و مرجع رسمی تطبیق دهید. روی شبکهٔ موجود، به‌جای ساخت سرویس دوم، ابتدا وضعیت فعلی را بخوانید.

۳. دریافت lease در کدام مرحله متوقف شده است؟

تبادل رایجِ تخصیص اولیه در RFC2131 بخش۳.۱ به چهار مرحله خلاصه می‌شود؛ تمدید lease یا کلاینتی که آدرس قبلی را می‌شناسد الزاماً همهٔ این مراحل را تکرار نمی‌کند.

Client        DHCP server
  DISCOVER ->    find servers
           <- OFFER
  REQUEST  ->    choose/confirm parameters
           <- ACK
Then compare the client configuration with the agreed plan.
  • بدون شاهد دریافت DISCOVER در سمت سرور، نتیجه نگیرید «pool خراب است»؛ رابط کلاینت، VLAN/مسیر broadcast و در شبکهٔ دیگر relay را بررسی کنید.
  • اگر OFFER دیده می‌شود ولی REQUEST یا ACK به نتیجه نمی‌رسد، مسیر رفت‌وبرگشت، انتخاب سرور و پارامترها را بررسی کنید. صرف وجود یک ردیف lease اثبات دریافت تنظیم درست توسط همان کلاینت نیست.
  • اگر کلاینت آدرس گرفته، IP/prefix، gateway، DNS و هویت سروری را که پاسخ داده با طرح تطبیق دهید؛ خطای DNS می‌تواند پس از تخصیص صحیح IP باقی بماند.
  • برای تشخیص مرحله، دادهٔ هم‌زمانِ کلاینت و سرور لازم است. این شکل خروجی capture واقعی نیست. اگر capture مجاز لازم شد، محدوده/زمان آن و حذف دادهٔ حساس را پیش از اشتراک روشن کنید.

راهنمای عیب‌یابی DHCP مایکروسافت هم دامنهٔ اثر، تغییرات اخیر، ظرفیت scope، آدرس دستیِ خارج‌نشده از scope و وضعیت relay را جدا بررسی می‌کند. جزئیات سرویس Microsoft DHCP را با RouterOS یکسان فرض نکنید.

۴. ابتدا وضعیت را بخوانید؛ release و reset آزمون خواندنی نیستند

# RouterOS — inspection only; output can contain private topology/identifiers
/ip/address/print detail
/ip/pool/print detail
/ip/dhcp-server/print detail
/ip/dhcp-server/network/print detail
/ip/dhcp-server/lease/print detail
/ip/dns/print

روی کلاینت Windows، مطابق ipconfig، دستور زیر تنظیمات کامل آداپتورهای فیزیکی و منطقی را نشان می‌دهد. آداپتور واقعاً درگیر، DHCP Enabled، آدرس/prefix، DHCP Server، زمان lease و DNS Servers را بررسی کنید؛ اطلاعات یک VPN یا آداپتور خاموش را به LAN نسبت ندهید.

ipconfig /all

خروجی می‌تواند آدرس، نام دستگاه و شناسهٔ سخت‌افزار داشته باشد؛ نسخهٔ کامل را عمومی منتشر نکنید. /release آدرس DHCP را کنار می‌گذارد و می‌تواند همان مسیر ریموت را قطع کند؛ flushdns هم cache را تغییر می‌دهد. این‌ها جای ثبت شواهد اولیه نیستند و در این مسیر عیب‌یابی اجرا نمی‌شوند.

۵. Reservation، آدرس دستی و تداخل را از هم جدا کنید

  • در reservation/static lease، کلاینت همچنان از DHCP می‌پرسد؛ سرور برای هویت تعیین‌شده آدرس مشخص می‌دهد. IP دستی روی خود دستگاه تنظیم می‌شود و دریافت آن وابسته به DHCP نیست.
  • طبق مفاهیم DHCP در RouterOS، client identifier و MAC در تشخیص کلاینت اهمیت دارند؛ همان شناسه‌ای را که سرور واقعاً دیده ثبت کنید. تعویض کارت یا تغییر شناسه می‌تواند تطبیق قبلی را بی‌اثر کند.
  • آدرس‌های دستی را در برنامهٔ تخصیص ثبت و از محدودهٔ تخصیص پویای هم‌پوشان خارج کنید. در طرح ساختگی، printer .60 و DNS .53 بیرون pool .100 تا .150 هستند؛ این توصیه به معنی ممنوع‌بودن reservation مدیریت‌شده در خود pool نیست.
  • در RouterOS، conflict-detection برای آدرس‌های پویا از ARP و ICMP استفاده می‌کند؛ static lease همان بررسی تعارض را ندارد. بنابراین «static شده» دلیل آزادبودن IP نیست. وضعیت conflict یا declined شاهدی برای بررسی است، نه مجوز پاک‌کردن همهٔ leaseها.

برای احتمال IP تکراری، زمان اختلال، مالک ثبت‌شدهٔ آدرس، lease همان کلاینت و شواهد ARP/پورت شبکه را کنار هم بگذارید. تغییر MAC به‌تنهایی اثبات تعارض نیست؛ proxy ARP یا افزونگی مجاز هم باید در طرح شناخته شده باشند. پاک‌کردن cache یا تغییر تصادفی IP پیش از ثبت شواهد می‌تواند تشخیص را دشوار کند.

۶. DNS خودِ روتر و DNS کلاینت دو آزمون متفاوت‌اند

در راهنمای DNS میکروتیک، router resolver می‌تواند برای خود روتر lookup انجام دهد یا به دستگاه‌های دیگر هم پاسخ بدهد. موفقیت resolve روی روتر ثابت نمی‌کند کلاینت همان DNS را می‌پرسد یا به آن دسترسی دارد. کلاینتی که DNS دیگری دریافت کرده، رکورد محلی روتر را لزوماً نمی‌بیند.

مرز مهمِ سرویس: allow-remote-requests=yes پاسخ‌گویی DNS روی UDP و TCP پورت۵۳ِ آدرس‌های روتر را ممکن می‌کند. در شبکهٔ دارای قواعد سفارشی، دسترسی باید فقط برای کلاینت‌های مورداعتماد و در سمت input مناسب محدود شود و از سمت اینترنت باز نماند. فعال‌کردن این گزینه یک قدم عمومیِ عیب‌یابی نیست. نمونهٔ این درس از DNS جدا استفاده می‌کند و آن را فعال نمی‌کند؛ قواعد firewall را نیز بدون شناخت رابط‌ها و مسیر مدیریت کپی نکنید.

۷. به‌جای دو ping متفاوت، یک پرسش DNS کنترل‌شده بپرسید

ابتدا نام کاملِ مورد انتظار، نوع رکورد و DNS مجاز را از طرح لاب انتخاب کنید. نمونهٔ زیر برای Windows دارای cmdlet مربوط است؛ مقدار واقعیِ مجاز را خودتان وارد می‌کنید و این متن آن را اجرا نکرده است. مرجع Resolve-DnsName، Server را برای انتخاب resolver، DnsOnly را برای کنارگذاشتن LLMNR/NetBIOS و NoHostsFile را برای کنارگذاشتن Hosts توضیح می‌دهد.

# Windows PowerShell — authorized lab query only, no configuration change
Get-Command Resolve-DnsName
$LabDnsName = Read-Host 'Enter the approved full lab record name'
$LabDnsServer = Read-Host 'Enter the approved lab DNS server IP'
Resolve-DnsName -Name $LabDnsName -Server $LabDnsServer -Type A -DnsOnly -NoHostsFile
  • پاسخ مورد انتظار: نام، نوع و آدرس پاسخ را با همان رکورد طرح مقایسه کنید؛ resolve شدن یک نام عمومی، صحت نام داخلی را اثبات نمی‌کند.
  • NXDOMAIN با timeout یکی نیست: اولی پاسخ منفی دربارهٔ وجود نام است؛ timeout یعنی پاسخ در بازهٔ انتظار به ابزار نرسیده است. نام/سرور اشتباه و مسیر دسترسی را جدا بررسی کنید.
  • SERVFAIL را با «نام وجود ندارد» یکی نگیرید؛ resolver نتوانسته پاسخ قابل استفاده بدهد. علت می‌تواند به upstream یا فرایند resolution مربوط باشد و نیاز به بررسی همان سرویس دارد.
  • حتی NOERROR می‌تواند برای نوع رکورد درخواستی پاسخ خالی داشته باشد. موفقیت DNS هم سلامت برنامه یا مجازبودن ترافیک آن را ثابت نمی‌کند؛ ping به IP دیگر و نامی دیگر فقط یک سرنخ اولیه است.

برگهٔ پذیرش لاب و گزارش نتیجه

  • قبل از اجرا: نسخه‌ها، طرح خصوصیِ جایگزین، رابط/bridge، pool و مالک آدرس‌های دستی، DNS و رکورد آزمون نوشته شده باشند.
  • پس از بررسی: تنظیم واقعیِ همان آداپتور و lease/هویت سرور با طرح تطبیق داده شود؛ دریافت آدرس از سرور ناشناس یا با prefix اشتباه پذیرش نیست.
  • تصمیم on-link/gateway برای دو مقصد مشخص با prefix و جدول مسیر توضیح داده شود؛ علت احتمالی با نتیجهٔ اندازه‌گیری‌شده مخلوط نشود.
  • پرسش یکسانِ نام/نوع/سرور و زمان مشاهده ثبت شود؛ خطای منفی، timeout و موفقیت DNS از آزمون برنامه جدا بمانند.
  • اقدام مجاز، روش بازگشت و موارد هنوز بررسی‌نشده ثبت شوند. تا اجرای واقعی، نتیجهٔ هر خانه «اندازه‌گیری نشده» است؛ این متن هیچ لاب موفق یا زمان بازیابی گزارش نمی‌کند.

اگر مسئله در شبکهٔ واقعی ادامه دارد، پشتیبانی شبکه تهران برای حضوری تهران و ریموت سراسر ایران، یا خدمات میکروتیک مسیر مرتبط است؛ شرح خطا را پس از حذف اطلاعات حساس بفرستید. جلسهٔ بعد: مسیریابی استاتیک؛ بازگشت به دورهٔ MTCNA.
