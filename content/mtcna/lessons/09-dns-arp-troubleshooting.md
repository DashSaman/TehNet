> پیش‌نویس مستقل آموزشی تهنت، کوتاه‌شدهٔ تهران نتورک؛ اجرای آزمایشگاه و تهیهٔ تصاویر هنوز انجام نشده است. مبنای برنامه‌ریزی RouterOS 7.25.1 و WinBox 4.5 است؛ نمایش نسخهٔ 7.26 در مستندات جدید، تأیید اجرای این تمرین روی آن نسخه نیست. همهٔ نتیجه‌ها «مورد انتظار» هستند. این متن ادعای تطبیق با ویدئوی منتشرشده یا آزمون رسمی جدید ندارد.

## پاسخ سریع

وقتی یک سایت با نام باز نمی‌شود، ابتدا دسترسی IP را جداگانه بررسی کنید. DNS نام را به اطلاعات آدرس تبدیل می‌کند؛ ARP برای پیدا کردن نشانی سخت‌افزاری همسایهٔ IPv4 روی همان شبکهٔ محلی است. تغییر تصادفی DNS نمی‌تواند کابل قطع، ماسک اشتباه یا گیت‌وی نادرست را اصلاح کند. هدف این درس آن است که برای هر نشانه، آزمایشی انتخاب کنیم که فقط یک فرضیه را بررسی کند.

## هدف‌ها و پیش‌نیاز

باید بتوانید یک خروجی ناموفق را به پرسش بعدی تبدیل کنید: آیا کلاینت به روتر می‌رسد؟ آیا همسایهٔ مستقیم پیدا شده؟ آیا خود روتر نام محلی را می‌شناسد؟ داشتن یک پاسخ موفق، فقط همان مسیر و همان لحظه را تأیید می‌کند. آشنایی با IP، ماسک و ترمینال لازم است. این تمرین به اینترنت، DNS عمومی یا DHCP نیاز ندارد و فقط در شبکهٔ جداشده انجام می‌شود.

## آدرس‌بندی آزمایشگاه

R1 روی ether2 آدرس 10.77.10.1/24 دارد؛ کلاینت روی همان سگمنت 10.77.10.10/24 و گیت‌وی 10.77.10.1 است. اگر از درس بریج استفاده می‌کنید، آدرس روتر روی bridge-lan قرار دارد و باید نام این رابط را در بررسی‌ها جایگزین کنید. ether1 به سمت بالادست آزمایشگاهی رزرو است و در این درس استفاده نمی‌شود. پیش از تغییر، خروجی IP > Addresses و IP > DNS را یادداشت کنید؛ تنظیم DNS سیستم کلاینت هم بخشی از وضعیت اولیه است.

## مراحل اجرا

۱. **دسترسی عددی را بررسی کنید.** از کلاینت سه بار 10.77.10.1 را ping کنید. سپس از روتر، کلاینت را با مبدأ مشخص آزمایش کنید. در WinBox از Tools > Ping استفاده کنید؛ Address مقصد و Src. Address مبدأ است. این دو جهت را یکی فرض نکنید: فایروال سیستم‌عامل کلاینت ممکن است درخواست ورودی را پاسخ ندهد.

```routeros
/ping address=10.77.10.10 src-address=10.77.10.1 count=3
/ip address print detail where interface=ether2
/ip arp print detail where address=10.77.10.10
```

نتیجهٔ مورد انتظار، وجود نشانی درست روی رابط درست و پس از ایجاد ترافیک، یک ورودی همسایهٔ قابل استفاده است. نبودن ورودی پیش از ترافیک الزاماً خطا نیست. MAC را با کارت شبکهٔ واقعی کلاینت مقایسه کنید؛ یک IP تکراری می‌تواند پاسخ را از دستگاه اشتباه برگرداند. نام یا رنگ وضعیت در رابط گرافیکی را به‌تنهایی معیار قرار ندهید.

۲. **مسیر همسایه را توضیح دهید.** برای مقصدی در همین /24، روتر باید MAC خود مقصد را پیدا کند. برای مقصد دور، MAC گام بعدی روی شبکهٔ خروجی لازم است، نه MAC سرور دوردست. بنابراین نبودن IP یک وب‌سایت در ARP طبیعی است. در WinBox پنجرهٔ IP > ARP را با ستون Interface و Address بخوانید. فعال کردن proxy-arp یا افزودن ARP ثابت، نخستین درمان این آزمایش نیست؛ ممکن است مشکل طراحی را پنهان کند.

۳. **یک نام محلی بسازید.** در IP > DNS > Static یک رکورد A با نام زیر و آدرس کلاینت اضافه کنید. نام `.test` برای این سناریوی محلی انتخاب شده و ادعای ثبت عمومی دامنه ندارد. نام باید فقط یک رکورد آزمایشی با این توضیح داشته باشد؛ اگر از قبل موجود است، دوباره اضافه نکنید.

```routeros
/ip dns static add name=pc09.tehnet.test type=A address=10.77.10.10 ttl=5m comment="TEHNET-L09-name"
:put [:resolve "pc09.tehnet.test"]
/ip dns static print detail where comment="TEHNET-L09-name"
```

خروجی مورد انتظار resolve برابر 10.77.10.10 است. این آزمایش، resolver خود روتر را می‌سنجد. موفقیت آن ثابت نمی‌کند که روتر به درخواست DNS کلاینت جواب می‌دهد، زیرا آن قابلیت تنظیم جداگانه دارد. در این درس `allow-remote-requests` را تغییر نمی‌دهیم؛ با همین تفکیک می‌توان بخش بزرگی از خطاهای تشخیصی را حذف کرد.

۴. **آزمون کلاینت را با شرایطش تفسیر کنید.** در سیستم‌عامل کلاینت، فرمان `nslookup pc09.tehnet.test 10.77.10.1` فقط وقتی باید پاسخ بگیرد که پاسخ‌گویی DNS روتر قبلاً برای LAN مجاز و فایروال مناسب تنظیم شده باشد. Timeout در غیر این صورت شکست رکورد ثابت نیست. روشن کردن سرویس برای رفع این timeout، بدون محدود کردن درخواست‌های ورودی UDP و TCP پورت 53 از سمت بالادست، کار این درس نیست. اگر سرویس فعال بوده، آدرس سرور نمایش‌داده‌شده در nslookup را ثبت کنید؛ مرورگر ممکن است از resolver دیگری استفاده کند.

۵. **یک خرابی بی‌خطر ایجاد کنید.** فقط رکورد آزمایشی را موقتاً غیرفعال کنید، resolve را تکرار کنید، سپس آن را برگردانید. اگر پاسخ قدیمی باقی بود، TTL و کش را در نظر بگیرید؛ جدول DNS و ARP دو کش متفاوت‌اند. به‌جای خالی کردن همهٔ جدول‌ها، منتظر انقضای پاسخ آزمایشی بمانید و یک پرس‌وجوی تازه انجام دهید.

```routeros
/ip dns static disable [find where comment="TEHNET-L09-name"]
/ip dns static enable [find where comment="TEHNET-L09-name"]
```

## جدول عیب‌یابی

| نشانه | بررسی بعدی | برداشت مجاز |
|---|---|---|
| ping گیت‌وی شکست می‌خورد | کابل، VLAN مجازی، ماسک و رابط | هنوز دلیلی برای تغییر DNS نداریم |
| ARP کلاینت ناقص می‌ماند | روشن بودن میزبان و اتصال همان سگمنت | رسیدن لایهٔ دو باید بررسی شود |
| resolve روتر درست، nslookup کلاینت timeout | فعال بودن سرویس و فیلتر input | رکورد ثابت لزوماً خراب نیست |
| نام به IP دیگری می‌رود | سرور استفاده‌شده و کش کلاینت | پاسخ ممکن است از resolver دیگری آمده باشد |

## تمرین و معیار پذیرش

یک برگهٔ چهارستونی بسازید: آزمون، مبدأ، مقصد، نتیجه. برای ping محلی، ARP و resolve هرکدام یک ردیف بنویسید. معیار موفقیت، توضیح ارتباط این سه ردیف است؛ تعداد پاسخ‌های ping جای تحلیل را نمی‌گیرد. سپس توضیح دهید چرا برای میزبان 10.77.20.10 نباید روی LAN1 انتظار ARP مستقیم داشت. در گزارش مشخص کنید کدام بررسی اجرا شده و کدام صرفاً پیش‌بینی بوده است.

## بازگشت محدود

فقط رکورد ساخته‌شده را حذف کنید. DNS سرور عمومی، ARP mode و تنظیمات کلاینت نباید به‌دلیل این تمرین تغییر کرده باشند. اگر از مسیر گرافیکی تنظیم دیگری را برای آزمایش شخصی تغییر داده‌اید، آن را طبق یادداشت اولیه برگردانید.

```routeros
/ip dns static remove [find where comment="TEHNET-L09-name"]
```
