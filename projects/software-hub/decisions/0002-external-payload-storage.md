# ADR 0002 — downloadable payloads stay outside the website VPS

Decision: owner instruction, 2026-10-17; supersedes local-CAS website recommendations in W0 v1 and the original research. Integrator owns this interface change. W2/W3/W5/W6 consumers in this release use this decision. Original research and schema 001 remain unchanged.

- Website disk contains application code, small public/restricted metadata registries, authentication and bounded operational state only. No software binaries, ISO/package/container archive cache, payload staging, disk-spooling proxy or local-CAS import command is included in the website engine.
- Public downloads start on TehNet and issue a 307 to an exact registered HTTPS mirror/object URL. The destination becomes visible. The browser downloads the payload directly; website bandwidth is used only for operator-run bounded verification. Provider Range/HEAD/redirect behavior remains the provider's responsibility and requires real acceptance tests. No claim that a redirect hides the origin or guarantees domestic tariffs.
- `ExternalRegistry` keeps separate public/restricted `external.sqlite` files. Registration requires explicit classification/license/provenance, an approved source policy, exact trusted SHA-256/size and a complete guarded network verification. Chunks are hashed in bounded memory and discarded immediately. No temporary payload file is created. Publication expires after one hour without re-verification; known expired public objects return 503. Metadata may remain listed with no promise of current availability.
- Private catalog and all private routes require live server-side session validation. Public redirects are **always refused** for restricted objects, including after login. A future external private backend must prove server-side authenticated retrieval or equivalent authorization on each request, revocation, no provider token exposure and no website disk buffering. This release deliberately returns 503 to an authenticated private download; anonymous known/unknown requests return the same 404. No private provider has been accepted.
- Missing files will be uploaded from the owner's workstation or a separate transfer worker **directly to external storage**, never staged on the website host. The upload worker is not implemented in this release. Do not silently restore local CAS to make an upload appear successful.
- Rubika is a candidate adapter, disabled until official API/permission, exact quotas, retention, link expiry, actual hash/Range/anonymous delivery and independent recovery are measured. No personal user session, unofficial quota rotation, token in Git, or assumed permanent/free storage.
- Migration moves code/images, metadata/auth and external credentials securely; provider payloads stay at their external locations. The target must have independent domestic access to those locations. This reduces website-state transfer but does not certify a 30-minute Iran cutover or availability during a complete external outage.

Implementation withdrawn before publication: the uncommitted local-CAS import/delivery/encrypted-payload-backup prototype and its tests. None was deployed or used for real software. Focused review identified an auth-schema completeness issue; a failing regression now verifies the fix in AuthStore. Its proposed CAS-backup restore code is absent from the final tree; no encrypted engine backup/restore acceptance is claimed.

Historical checkpoints describing CAS are history only. Current requirements, interfaces and acceptance are this decision plus [EXTERNAL_STORAGE](../EXTERNAL_STORAGE.md), [ENGINE_OPERATIONS](../deployment/ENGINE_OPERATIONS.md) and the latest STATUS entry.
