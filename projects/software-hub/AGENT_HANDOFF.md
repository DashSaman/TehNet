# تحویل جامع آرشیو نرم‌افزار تهران نتورک به ایجنت بعدی

**تاریخ جمع‌بندی: ۲۵ اکتبر ۲۰۲۶. آخرین شواهد عملیاتی این گفتگو: ۲۱ اکتبر ۲۰۲۶.** این جمع‌بندی از فایل‌های ریپو و نتایج ثبت‌شده تهیه شده است؛ امروز SSH، دانلود، نصب، انتشار یا بررسی زندهٔ جدیدی انجام نشده است. نسخه و منابع فعال امروز را از یک گزارش قدیمی نتیجه نگیرید.

این بخش از **تهران نتورک** است؛ محصول مستقلی به نام مخزن مبدأ نیست. محدودهٔ توسعه همین پوشه و محدودهٔ وب /software/ است. سایت اصلی WordPress، قالب، Core، محتوا، سرویس‌ها و پورت‌های دیگر خارج از محدوده‌اند. تغییر منوی مجاز، یک گزینهٔ دسترسی به این بخش بود.

## ۱. ترتیب شروع و مرجع معتبر

1. ابتدا [AGENTS ریشه](../../AGENTS.md)، سپس [AGENTS این بخش](AGENTS.md) و همین فایل را بخوانید.
2. [STATUS](STATUS.md)، [ROADMAP](ROADMAP.md) و [مالکیت کارها](WORKSTREAMS.md) را بخوانید. ثبت جدیدترِ یک کار مشخص، وضعیت قدیمی همان کار را به‌روز می‌کند؛ یک برنامهٔ کلی، مدرک اجرای همهٔ قابلیت‌هایش نیست.
3. برای ادامه، task مربوط و گزارش پذیرش آن را بخوانید؛ جدول بخش ۹ مسیرها را مشخص می‌کند.
4. branch، HEAD، تغییرات محلی و ref واقعی remote را بررسی کنید. تغییر دیگران را بازنویسی نکنید. پیش از ویرایش، مالک، زمان UTC، predecessor، مسیرهای متعلق به خود و وابستگی‌ها را در task ثبت کنید.
5. برای عملیات زنده، manifest و وضعیت مجاز فعلی را فقط‌خواندنی بررسی کنید؛ image، شناسهٔ کانتینر، SHA پروفایل یا ساعت اجرای تاریخی را مبنای امروز قرار ندهید. helper موقت یا فرمان استقرار قدیمی را کورکورانه تکرار نکنید.

مبنای این جمع‌بندی، ref عمومی **3c85cc3339b0d3e1ad74c82d8395d183948b9d4e** است. گزارش پایان ابتدا در **750513c35f30dfe79f37cd1a59857ec3a088664f** ثبت شد و سپس بازنشستگی ثبت شد. شاخهٔ مجاز docs/melika-consolidation-2026-10-17 و [PR شمارهٔ ۲](https://github.com/DashSaman/TehNet/pull/2) در بررسی ۲۵ اکتبر draft و ادغام‌نشده بودند. تغییر امروز فقط مستندات است.

## ۳. معماری و قرارداد ذخیره‌سازی

- [ADR 0002](decisions/0002-external-payload-storage.md) تصمیم نهایی مالک است: روی دیسک وب‌سایت، payload نرم‌افزار، CAS، staging، spool یا cache دانلود وجود نداشته باشد. کد برنامه و متادیتای کوچک/احراز هویت/وضعیت عملیاتی محلی‌اند. فایل واقعی از میرور یا ذخیره‌ساز بیرونیِ جداگانه پذیرفته‌شده دریافت می‌شود.
- آزمایش‌های مستقل موجود از RAM خصوصی موقت noswap استفاده می‌کنند؛ swap0، محدودیت cgroup، noOOM، نصب بدون شبکه و حفظ محیط باید در مدرک کامل باشند. این استثنای آزمایش، مجوز ذخیرهٔ payload روی دیسک سایت نیست.
- Python/FastAPI/Jinja2، SQLite تک‌نویسنده، ابزارهای امضا و HTTPS و اتصال زیرمسیر، مرزهای فعلی‌اند. فایل‌های برنامه و متادیتای عمومی با mountهای محدود اداره می‌شوند؛ معماری اصلی WordPress بازنویسی نشده است.
- درخواست دانلود عمومی پس از کنترل هویت و پذیرش به مقصد بیرونی می‌رود. redirect، مقصد را آشکار می‌کند؛ پنهان‌بودن IP/مقصد یا تعرفهٔ داخلی از آن نتیجه نمی‌شود.
- [EXTERNAL_STORAGE](EXTERNAL_STORAGE.md)، [امنیت و حریم](SECURITY_PRIVACY.md) و runbook مرتبط قبل از تغییر runtime خوانده شوند. هیچ URL ورودی آزاد، fallback خارجی خودکار یا منبع کشف‌شده بدون پذیرش فعال نشود.

## ۴. رمز VPN و روبیکا

رمز را مالک با ابزار تعاملی مخفی روی سرور انتخاب می‌کند؛ ما در این گفتگو رمز واقعی تعیین یا دریافت نکردیم. رمز، توکن، session، پایگاه خصوصی و فایل خصوصی نباید در چت، آرگومان، Git یا screenshot منتشر شوند. وضعیت تنظیم امروز مالک را از آزمون قدیمی فرض نکنید.

بخش VPN باید سمت سرور محافظت شود و از فهرست، API، شمارنده، cache و مسیرهای عمومی حذف بماند. پنهان‌سازی با JavaScript کافی نیست. ورود مجاز به صفحه نیز به‌معنی پذیرش backend تحویل خصوصی نیست. الگوی فعلی یک هویت محدود با رمز مشترک است، نه سامانهٔ نقش‌های چندکاربره.

برای رمز، [ENGINE_OPERATIONS](deployment/ENGINE_OPERATIONS.md) و برای توکن رسمی بات، [RUBIKA_PILOT](deployment/RUBIKA_PILOT.md) مرجع‌اند. ابزار روبیکا آماده شده، اما getMe/transport یا fixture به‌معنی آپلود/دانلود واقعی، ماندگاری ۲۴/۷۲ ساعت، Range، کنترل دسترسی و بازیابی نیست. backend روبیکا در آخرین پذیرش غیرفعال بود. فعال‌سازی آن بدون مدرک کامل، مجوز صریح و سهمیهٔ معتبر انجام نشود؛ session شخصی یا چرخش حساب/سهمیه مجاز نیست.

## ۵. زنجیرهٔ آفلاین و انتشار

1. از متادیتای امضاشده، candidate دقیق با نسخه، وابستگی، اندازه، SHA و indexهای لازم ساخته می‌شود.
2. candidate در Ubuntu Base 24.04.5 amd64 پاک و ایزوله، بدون شبکه نصب و کارکرد هشت ابزار و آزمون‌های منفی بررسی می‌شود.
3. فقط همان candidate پذیرفته‌شده منتشر می‌شود؛ مدرک نسل قبلی یا نصب جزئی جای آن را نمی‌گیرد.
4. کنترل‌کننده، چهار منبع آروان، LinuxMirrors.ir، لیارا و هم‌روش را برای SHA منتشرشده مستقلاً آزمایش می‌کند.
5. API و صفحهٔ انتخاب فقط نتیجهٔ معتبر همان SHA را نمایش می‌دهند. در فاصلهٔ انتظار نسل تازه، خالی‌بودن انتخاب درست است؛ pass قدیمی نباید نسل جدید را فعال کند.
6. ابزار دریافت نیز receipt همان نسل را پیش از دریافت بسته‌ها می‌خواهد. فایل‌ها روی دستگاه آماده‌سازی کاربر یا RAM آزمایش می‌آیند، نه دیسک وب‌سایت.

طبق قرارداد آزموده‌شده، publisher هر ۶ ساعت بررسی و پس از حداقل ۱۲ ساعت از پذیرش قبلی برای نسل تازه اقدام می‌کند. محدودیت ۴۸ ساعتهٔ client با سقف سخت‌گیرانه‌ترِ تازگی متادیتای mutable هنگام انتشار یکی نیست؛ در پذیرش publisher سقف ۲۴ ساعت ثبت شده است. کنترل Date/Valid-Until/ضدبازگشت امضا حفظ می‌شود. نوبت تقویمی پیش از حداقل ۱۲ ساعت می‌تواند به‌درستی not_due باشد؛ برای ساختن انتشار، ساعت یا guard را تغییر ندهید.

بودجهٔ publisher از بودجهٔ provider جداست. قرارداد provider شامل ۱۹۲ MiB برای هر intent، حداکثر چهار منبع در هر پروفایل و هشت تلاش/۱۵۳۶ MiB در روز UTC است. شکست و قطع نیز شارژ می‌شوند. intent ناموفق همان SHA/منبع حتی با عوض‌شدن روز دوباره اجرا نمی‌شود. این ارقام reservation هستند، نه اندازه‌گیری ترافیک واقعی. برای مقدار و وضعیت فعلی، runbook و ledger معتبر را بخوانید؛ آن‌ها را reset نکنید.

سه رخداد واقعی انتشار، سه SHA جدید و شمارندهٔ سه نسل مشاهده‌شده در نمونه‌های سالم جداگانه تطبیق داده شدند. آخرین نسلِ بررسی‌شده SHA برابر be34b7d12a2a77479c8846179aae95636c64b46701655fbe730605f57b7ee4f3 داشت؛ پذیرش در ۲۱ اکتبر 06:27:19.581939 UTC و رخداد واقعی انتشار در 06:27:22.108766 UTC ثبت شد. نتیجهٔ منابع فقط برای همین SHA بود:

| منبع | نتیجهٔ همان نسل |
| --- | --- |
| آروان | pass |
| لیارا | pass |
| هم‌روش | pass؛ نسل مستقل از شکست قبلی این منبع |
| LinuxMirrors | failed و غیرفعال؛ guard پاسخ HTTP/status/encoding رد کرد |

کد وضعیت یا header دقیق پاسخ LinuxMirrors در مدرک اصلی ثبت نشده بود؛ علت دقیق خارجی نامعلوم باقی ماند. چهار fixture بدون شبکه همان guard را بازتولید کردند. guard ضعیف نشد، مدرک ساخته نشد و همان intent تکرار نشد. شکست قبلی هم‌روش نیز پاک نشد.

۹ زنجیرهٔ امضای اصلی در زمان پذیرش، سه نصب canonical، ۱۰ مدرک کامل provider، ۱۶۰ هش کد، ۲۳ کنترل HTTPS و ۲۳ آزمون هدفمند در پایان بررسی شدند. این شمارنده‌ها نتیجهٔ همان بررسی‌اند؛ امروز دوباره اجرا نشده‌اند. تلاش اولیه با مفسر عمومی، خطای وابستگی pwdlib داشت؛ اجرای محیط توسعهٔ موجود ۲۳ آزمون را گذراند. خطاهای محلی CRLF/قالب گزارش و بازاعتبارسنجی تاریخی با ساعت جاری نیز در گزارش‌ها ثبت و اصلاح شدند؛ به ۴۲ خطای بومی سرور اضافه نمی‌شوند. امضای تاریخی را با زمان پذیرش بررسی کنید؛ این کار جای کنترل تازگی واقعی نسخهٔ جاری را نمی‌گیرد.

بعد از ثبت گزارش، فقط تایمر finite پایش غیرفعال/disabled و automation-4 حذف شد. دو تایمر بومی انتشار و provider-auto در آخرین کنترل فعال/enabled ماندند؛ [رسید واقعی بازنشستگی](evidence/OFFLINE_WATCH_RETIREMENT_20261021.json). این پیگیری پایان یافته را بدون درخواست تازهٔ مالک دوباره نسازید. روشن‌نبودن برنامهٔ محلی با توقف عملیات بومی سرور یکی نیست.

## ۷. بکاپ، بازگشت و مهاجرت

بازیابی رمزگذاری‌شدهٔ متادیتا و وضعیت احراز هویت، راه‌اندازی مستقل بدون شبکه، بازیابی با کلید تحت اختیار مالک و بازگشت کد روی همان میزبان آزموده شدند. فعال‌سازی ۸ ثانیه‌ای و تمرین بازگشت ۱۲ ثانیه‌ای در محدودهٔ آماده‌شده ثبت شدند؛ 502های کوتاه حین تعویض نیز حفظ شده‌اند. این اعداد زمان تهیهٔ کلید، نصب اولیه، WAN یا همگرایی DNS را پوشش نمی‌دهند.

**مهاجرت واقعی به ایران زیر ۳۰ دقیقه هنوز پذیرفته نشده است.** هدف، cutover مقصد ازپیش‌آماده با image/وابستگی‌های preloadشده، بکاپ سالم، کلید مالک، HTTPS/دامنه، TTL و کنترل DNS، ورودی مستقل و دسترسی مستقیم داخلی به منابع بیرونی است؛ نه انتقال نامحدود فایل در ۳۰ دقیقه.

[MIGRATION](deployment/MIGRATION.md) و [RECOVERY](deployment/RECOVERY.md) شروط و ترتیب را دارند. باید دو تمرین واقعی و زمان‌دار روی مقصد مستقل، smoke/public/private/provider و بازگشت پیش/پس از نوشتن ثبت شود. فقط یک نویسنده مجاز است؛ پس از نوشتن مقصد، rollback به توقف دو نویسنده و reconciliation نیاز دارد. بکاپ قدیمی را روی دادهٔ جدید restore نکنید. ورودی خارجیِ باقی‌مانده در مسیر حیاتی، استقلال هنگام اختلال را ثابت نمی‌کند.

## ۸. کارهای باز و حدود پذیرش

- W1: بستهٔ اصلی OFFLINE_SOFTWARE_CATALOG موجود نبود. پوشهٔ [رکورد ورودی مفقود](research/OFFLINE_SOFTWARE_CATALOG/README.md) خودِ کاتالوگ نیست. از حافظهٔ چت یا شمارنده‌های ادعایی بازسازی نشود؛ ورود آینده نیازمند فایل واقعی، هش، انتساب، ممیزی و آزمون است. طبق دستور مالک، این فقدان مانع توسعه با پژوهش موجود نبود.
- W4 کلی: پروفایل محدود پذیرفته شده؛ کل موتور عمومی APT/gap، همهٔ توزیع‌ها، booted VM و اکوسیستم‌های PyPI/npm/Docker به‌طور کلی کامل اعلام نشوند. taskهای فرعی پذیرفته‌شده از stub برنامهٔ اولیه جدا هستند.
- W2/W5: تنظیم مالک و تحویل خصوصی بیرونی/روبیکا، هرکدام پذیرش مستقل دارند. fixture و auth آماده، backend خصوصی پذیرفته‌شده نیستند.
- W7: میزبان ایرانی، مسیر و DNS، دو انتقال واقعی و rollback پس از نوشتن هنوز مدرک پذیرش ندارند.
- نیم‌بهاشدن، ثبت ملی، وام، دانش‌بنیان، تعرفه یا دسترسی داخل ایران اخذ یا اثبات نشده‌اند.
- نتیجهٔ منبع و نسخهٔ امروز نیازمند خواندن مجاز وضعیت امروز است. این درخواست فقط جمع‌بندی مستندات بود؛ هیچ آزمون یا انتشار تازه برای تغییر این نتایج اجرا نشده است.

## ۱۰. تقسیم کار و ثبت اجباری

[WORKSTREAMS](WORKSTREAMS.md) مرز مالکیت و وابستگی دقیق را تعیین می‌کند. ادغام‌کننده مالک README/AGENTS/STATUS/CHANGELOG/قراردادهای مشترک و یادداشت‌های ریشه است. فقط یک مالک برای هر task و مجموعه مسیرها؛ طرح موازی مجوز چند ایجنت نامحدود نیست.

| محدوده | مالک/وابستگی برای ادامه |
| --- | --- |
| W0 | قرارداد frozen؛ تغییر schema/نوع مشترک فقط با هماهنگی ادغام‌کننده |
| W1 | ممیزی ورودی و provenance؛ پیش از export runtime به قرارداد W0 وابسته است |
| W2 | احراز هویت و مسیر خصوصی؛ به W0 و قرارداد ذخیرهٔ بیرونی متکی است |
| W3 | netguard/transport و آزمون‌های TLS/peer/بودجه؛ قرارداد W0 |
| W4 | profile/publisher/provider tools و آزمون‌های خودش؛ W3 و قرارداد W5؛ مجوز تغییر auth/site ندارد |

| W7 | runbook/qualification/عملیات مهاجرت؛ release پذیرفته‌شده، کلید/مقصد/ورودی مجاز و یک نویسنده |

قبل از ویرایش، task را claim کنید؛ مالک فعلی باید مسیر را تحویل دهد. بعد از هر مرحله، واقعیت انجام‌شده، نتیجهٔ کامل آزمون، خطاها، محدودیت و قدم بعدی در task نوشته شود. ادغام‌کننده همان مرحله را در STATUS، CHANGELOG و PROGRESS/HANDOFF/TASKS ریشه ثبت می‌کند. کار بدون این تطبیق done نیست. ثبت‌های تاریخی را حذف یا به قبولی جدید تبدیل نکنید.

آزمون‌ها باید با مفسر و وابستگی‌های درست انجام شوند؛ شکست import مفسر عمومی، خرابی production نیست. [README](README.md) و lockfileهای توسعه مرجع آماده‌سازی‌اند. در محیط این مالک، RTK رعایت و خروجی unittest کامل نگه داشته شود. از ریشهٔ ریپو:

~~~sh
rtk proxy python -B projects/software-hub/tools/verify_consolidation.py
~~~

برای آزمون کد، از پوشهٔ این بخش و محیط توسعهٔ درست:

~~~sh
rtk proxy python -B -m unittest discover -s tests -v
~~~

آزمون‌های مخصوص Linux/GPG که روی Windows skip می‌شوند را روی Linux مربوط اجرا و جدا ثبت کنید. این فرمان‌ها آزمایش زندهٔ دانلود/نصب یا مهاجرت محسوب نمی‌شوند. برای تغییر صرف مستندات، کنترل منشأ، لینک‌ها، scope، حریم و diff کافی است؛ فقط برای ساختن قبولی، lab/refresh/collector اجرا نکنید.

انتشار فقط روی شاخهٔ مجاز، پس از آزمون و خواندن diff کامل و تأیید ref واقعی انجام شود. force-push، merge main، git add گستردهٔ شواهد، انتشار شاخهٔ خصوصی یا فرستادن raw log/snapshot/رمز/مسیر سرور و شناسهٔ داخلی مجاز نیست. فقط خلاصهٔ پالایش‌شده و دادهٔ پذیرش عمومی منتشر شود؛ اصل شواهد خصوصی و شکست‌ها حفظ بمانند.
